RWLock(Read-Write Lock, 읽기-쓰기 락)은 **읽기(Read)와 쓰기(Write)를 구분하여 동시성을 높이기 위한 동기화 기법**이다.

핵심 아이디어는 다음 한 문장으로 요약된다.

> **읽기는 여러 스레드가 동시에 허용하지만, 쓰기는 한 번에 하나만 허용한다.**

---

## 왜 필요한가?

뮤텍스는 읽기든 쓰기든 모두 하나씩만 접근할 수 있다.

예를 들어 캐시를 조회하는 스레드가 100개 있고, 모두 단순 조회만 한다면 서로 영향을 주지 않는다.

그런데 뮤텍스를 사용하면

```
Thread A (읽기)  ← 실행
Thread B (읽기)  ← 대기
Thread C (읽기)  ← 대기
```

읽기끼리는 충돌하지 않는데도 순차적으로 실행되어 성능이 떨어진다.

RWLock을 사용하면

```
Thread A (읽기)  ← 실행
Thread B (읽기)  ← 실행
Thread C (읽기)  ← 실행
```

여러 읽기 작업을 동시에 수행할 수 있다.

---

## 동작 방식

### 1. 읽기 락(Read Lock)

```text
Reader A → lock_shared()
Reader B → lock_shared()
Reader C → lock_shared()
```

모두 동시에 접근 가능.

---

### 2. 쓰기 락(Write Lock)

```text
Writer A → lock()
```

쓰는 동안에는

* 다른 Writer도 못 들어오고
* Reader도 못 들어온다.

```
Writer A ← 실행

Reader B ← 대기
Writer C ← 대기
Reader D ← 대기
```

---

## 상태를 그림으로 보면

### 여러 Reader

```
Reader1   ✔
Reader2   ✔
Reader3   ✔
```

가능

---

### Reader + Writer

```
Reader1   ✔
Writer1   ✖
```

불가능

---

### 여러 Writer

```
Writer1   ✔
Writer2   ✖
```

불가능

---

## C++ 예시

```cpp
std::shared_mutex rwlock;
```

읽기

```cpp
rwlock.lock_shared();

// 읽기

rwlock.unlock_shared();
```

쓰기

```cpp
rwlock.lock();

// 수정

rwlock.unlock();
```

## 언제 사용하는가?

### 1. 캐시(Cache)

```
95% 조회
5% 갱신
```

조회가 대부분이라 Reader를 동시에 실행시키는 것이 효율적이다.

---

### 2. 설정(Configuration)

프로그램 설정은

* 읽기는 계속 발생
* 변경은 거의 없음

이럴 때 RWLock이 적합하다.

---

### 3. 게임 서버

예를 들어

* 플레이어 정보 조회
* 랭킹 조회

는 매우 많고,

* 랭킹 갱신

은 상대적으로 적다.

---

### 4. 메모리 데이터베이스

읽기 요청이 압도적으로 많다면 RWLock으로 성능을 높일 수 있다.

---

## 뮤텍스와 비교

| 상황              | 뮤텍스     | RWLock                |
| --------------- | ------- | --------------------- |
| Reader 2명       | 한 명만 가능 | 둘 다 가능                |
| Writer 2명       | 하나만 가능  | 하나만 가능                |
| Reader + Writer | 하나만 가능  | Writer가 Reader를 모두 막음 |

---

## 단점

### 1. Writer Starvation(기아)

Reader가 계속 들어오면 Writer가 영원히 기다릴 수도 있다.

예를 들어

```
Reader
Reader
Reader
Reader
Reader
...
```

Reader가 끊임없이 들어오면 Writer가 실행 기회를 얻지 못하는 구현도 있다.

이를 해결하기 위해 많은 구현은 **Writer 우선 정책**, **Reader 우선 정책**, 또는 **공정(Fair) 정책**을 제공한다.

---

### 2. 구현이 뮤텍스보다 복잡하다.

Reader 수를 관리해야 하고,

Writer와의 충돌도 관리해야 하므로 구현 비용이 높다.

---

### 3. 읽기와 쓰기가 비슷하게 많이 발생하면 효과가 거의 없다.

예를 들어

```
읽기 50%
쓰기 50%
```

Writer가 자주 등장해 Reader를 계속 막기 때문에 결국 뮤텍스와 큰 차이가 없어질 수 있다.

---

## 언제 RWLock을 쓰는가?

다음 조건을 만족하면 사용하는 것이 좋다.

* **읽기 작업이 대부분이다.**
* **쓰기 작업은 드물다.**
* **읽기끼리는 서로 영향을 주지 않는다.**

반대로 쓰기 작업이 자주 발생하거나 임계 구역이 매우 짧다면, RWLock의 관리 비용 때문에 오히려 **뮤텍스가 더 적합**한 경우도 많다.

### 한 줄 요약

> **뮤텍스는 "한 번에 하나만" 접근하도록 하는 락이고, RWLock은 "읽기는 여러 개, 쓰기는 하나만" 허용하여 읽기 중심 워크로드의 성능을 높이는 락이다.**
